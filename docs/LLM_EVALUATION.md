### Что реализовано

`baikal/source_first.py` отделяет source-only вход от статьи и known_issues; использует прежние точные фрагменты 2016/PDF 222 и 2015/PDF 26. Цитаты привязываются по ID, источники/страницы/версии сверяются с локальными checkpoint. До шести атомарных фактов с годом наблюдения, показателем, единицей, территорией, типом сообщения и ограничениями; противоречия — отдельные записи. Неизвестный ID, свободно переписанная цитата, неподдержанное число, год только из метаданных или неполный контракт блокируются. Проверка чисел не доказывает соответствия показателя/единицы или смысловой поддержки.

Программно допустимые факты требуют отдельной source-comparison сверки с решением по каждому ID, причиной и ограничениями. Решение привязано к хешу пакета, не может менять факт и не присваивает статуса эксперта/verified observation. Только после этой границы второй этап получает статью и неизменные факты. Его контракт запрещает переписывать их текст/источники, требует решение по каждому ID и точную подстроку статьи для повтора/противоречия. Для новых деталей программа копирует исходный факт в отдельный карантин черновиков. Путь автоматического переноса в статьи/observations отсутствует.

Runner `scripts/evaluate_source_first.py` сохраняет immutable manifest с SHA256 протокола, кода, промптов, прежних входов и статей. Эксклюзивный маркер попытки создаётся до HTTP; повтор того же случая/этапа запрещён даже при ошибке. В реальном опыте дополнительно проверено, что попытка сравнения отклонённого извлечения завершается до запуска runtime/генерации. Положительные пути gate, классификации и сохранения черновика проверены **только синтетически**, не настоящей моделью.

### Причины, ограничения и следующий шаг

Изоляция первоисточника и безопасная остановка работают программно. Рост числа записей не улучшил готовность знаний: ограничения не переданы, известная неоднозначность потеряна, целевая деталь выпуска пропущена. Контекст короткий и не усечён, поэтому нехватка окна не объясняет эти конкретные отказы. JSON парсится; валидатор правильно отклоняет реально пустые поля. Смысловое чтение таблицы осложнено плоским извлечением заголовков; его вклад и ограничения модели нельзя разделить по двум случаям. Специализированный режим остаётся **экспериментальным**, основной механизм публикации не заменён. Реальный двухэтапный цикл ещё не подтверждён.

Следующий спринт — один заранее ограниченный тест извлечения до повторного сравнения с Wiki: локальное структурированное декодирование обязательных типов/списков, явные временные роли и точные evidence-spans; отдельно проверенное соответствие столбцов **только этой одной таблицы 2015** с сохранением исходной прозы и обоих противоречивых значений. Не вставлять общие ограничения/одобрения программой и не исправлять числовые данные. Структурное декодирование не гарантирует достоверного ограничения, это тоже критерий проверки. К новизне переходить только после получения полного поддержанного факта. Новая модель, повтор прежних запросов и массовая обработка PDF/OCR для этого не нужны.

Проверки provenance этого опыта: `python scripts/check_source_first.py --require-local` — четыре неизменных фрагмента, две сырые записи, прежние входы и два использованных слота. Полный запуск/границы второго этапа описаны в [SOURCE_FIRST.md](SOURCE_FIRST.md). Итоговые тесты и сохранность зафиксированы в PROGRESS.md. Статьи, verified наблюдения и реестры не менялись; научная рецензия не заявляется.

Смысловую поддержку всё равно нужно отдельно проверить; результат требует редакционного решения. Это конкретный следующий тест архитектуры, а не новый круг настройки маленькой модели. В этом спринте он не запускался.

## Runtime: почему потребовалась совместимая сборка

Прежняя сборка llama.cpp была использована первой, без пересборки. `--version` работал, но процесс сервера завершился до загрузки модели с пустым журналом. Дополнительный `--list-devices`, инициализирующий backend без модели, завершился с кодом **−4 / SIGILL**. Счётчики OOM cgroup равны нулю. Старые параметры содержат `GGML_NATIVE=ON` и `-march=native`. В текущей среде CPU AMD EPYC 7763 поддерживает AVX2/FMA/F16C, но не AVX-512. Вероятная причина — несовместимость native-сборки с CPU новой среды; конкретная аварийная инструкция не установлена.

Поэтому из тех же закреплённых исходников собран **отдельный** `data/llm-runtime/build-avx2/`; прежний `build/` сохранён. Использованы `GGML_NATIVE=OFF`, AVX/AVX2/FMA/F16C — ON, AVX-512 и CUDA — OFF, четыре задания сборки. Это необходимое устранение воспроизведённого сбоя, а не повторная плановая сборка. CMake 4.4.4, GNU C++ 14.2.0; исходный tag `v0.7.0`, commit `620d2225cc436ab0b001e3200e590e3b286ef9ab`.

Совместимый runtime успешно прошёл `--version`, `--list-devices`, загрузку модели и два запроса. Версия `0.7.0-dev (build 1, commit 620d222)`, SHA256 бинарного файла `ea2082a6ea129e3fbe0e32c4a57cf0fd754572b5a0fb824b89b9ed80b64836f6`. Контрольные суммы shared libraries включены в протокол. Вывод `Available devices: (none)` означает отсутствие перечисляемых GPU-устройств, CPU-инференс работает.

В `evaluate_local_llm.py` добавлена проверка backend через `--list-devices`: успешного `--version` больше недостаточно. SIGILL и другие ошибки инициализации сообщаются до запуска модели; неожиданное завершение сервера теперь включает код и путь журнала. Два новых синтетических регрессионных теста проверяют этот механизм. Они не заменяют реальные ответы ниже.

Не менять промпт или исправлять ответ незаметно: новые настройки требуют отдельной версии опыта.

## Редакционное принятие без автоматической публикации

Оба реальных ответа отклонены до сохранения допустимых черновиков. Человеческого одобрения и применения дополнений к проекту в этом спринте **не было**. Переход проверен только синтетическими fixtures в изолированных каталогах, включая непустые заметки и откат ошибки записи. Это не имитация научной рецензии.

После будущей генерации можно подготовить дополнение из выбранных кандидатов `new_detail` (индексы от нуля):

```bash
python -m baikal prepare-change --draft DRAFT_ID --claims 0
```

Открыть полученный пакет `data/wiki_updates/changes/CHANGE_ID.json`: проверить `new_text`, выбранные утверждения, ссылки, ограничения и контрольные суммы. Подготовка ничего не меняет в статье. Редактор должен сам сверить смысл, год, территорию, единицы и неопределённость. Следующий шаблон намеренно **не является одобрением** и будет отклонён до реального заполнения:

```json
{
  "change_id": "CHANGE_ID",
  "decision": "approve",
  "review_kind": "editorial",
  "reviewed_by": "",
  "reviewed_at": "YYYY-MM-DD",
  "source_semantics_checked": false,
  "uncertainties_preserved": false,
  "test_only": false
}
```

После реального редакционного решения:

```bash
python -m baikal apply-change --change CHANGE_ID --approval data/editorial-approval.json
python -m baikal build
python -m baikal lint
```

Изменение привязано к точной версии статьи и immutable-черновика; устаревший источник, текст или неподдержанная цитата блокируют применение. Старый основной текст сохраняется, дополнение помещается перед неизменными HUMAN NOTES, предыдущая версия архивируется. Источники добавляются к прежнему происхождению, решение фиксируется в `datasets/editorial_changes.json` и журнале Wiki. Ошибка записи вызывает откат. Повторное применение не дублирует дополнение.

Прежний реестр научной проверки не переписывается: изменившийся основной текст теряет действующий статус прежней сверки и требует проверки дополнения. Редакционное принятие не даёт статуса специалиста и не добавляет числа в observations. Тестовые одобрения `test_only=true` запрещены в настоящем репозитории. Новые статьи требуют отдельного редакционного процесса, а не автоматического создания из кандидата.

## Сохранность и следующий шаг

Все 22 статьи, 168 проверенных наблюдений, научные реестры и источники сохранились побайтово: SHA256 28 защищённых файлов совпали с началом спринта. Wiki lint и проверки 162 доказательных ссылок научного реестра, 47 записей энциклопедии, 168 наблюдений выполняются без ошибок.
